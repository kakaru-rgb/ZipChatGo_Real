부동산 지도 웹서비스 + AI Agent 개발 계획 정리
작성 기준: 2026-09-01

============================================================
1. 최종 목표
============================================================

최종적으로 만들고 싶은 서비스는 단순한 부동산 챗봇이 아니라,

"지도 상태를 이해하고, 부동산 DB를 검색하고, 지도 UI까지 제어할 수 있는 AI Agent"

이면서 동시에,

"웹사이트 구조 + 현재 사용자 상태 + 서비스 데이터 + 실행 가능한 UI Tool을 이해하는 AI Agent"

이다.

즉 사용자가 메뉴를 거의 직접 누르지 않고, 자연어 대화만으로 다음 흐름을 이용할 수 있는 서비스를 목표로 한다.

지도
→ 매물 검색
→ 매물 선택
→ 지역/매매가 분석
→ 관심매물 등록 및 비교
→ 주변 POI 확인
→ 부동산 법률 상담

예시)

사용자:
"판교역 근처 8억 이하 아파트 찾아줘."

AI:
- 사용자의 의도와 조건을 이해
- 매물 검색 Tool 호출
- Spring Boot의 매물 API를 통해 DB 검색
- 검색 결과 중 적합한 매물 선택
- Frontend에 판교역으로 지도 이동 명령 전달
- 해당 매물 마커 강조
- 자연어로 매물 특징 설명

사용자:
"두 번째 매물 찜해줘."

AI:
- 현재 화면에서 두 번째 매물이 어떤 매물인지 Context를 통해 확인
- 관심매물 등록 Tool 호출
- Spring Boot의 관심매물 API 실행
- 관심매물 등록 결과 설명

사용자:
"이 매물이 있는 지역의 최근 매매가 흐름도 보여줘."

AI:
- 매물 검색 Tool 호출
- 해당 매물의 위치 확인
- 해당 지역/역 자동 선택
- 매매 유형 자동 선택
- 분석 실행
- 기존 웹페이지의 그래프 및 분석 데이터를 화면에 표시
- 같은 원본 분석 데이터를 AI도 받아 자연어로 해석

사용자:
"이 집 전세 계약할 때 주의할 법적인 부분은?"

AI:
- 법률 관련 질문으로 판단
- 부동산법 RAG Tool 사용
- 최신 법률 문서에서 관련 내용을 검색
- 근거를 바탕으로 설명


============================================================
2. 전체 시스템 구조
============================================================

전체 서비스는 다음과 같이 구성한다.

[Frontend]
현재 만들어 놓은 HTML/CSS/JavaScript
- 네이버 지도
- 매물 목록
- 매물 상세
- 관심매물
- 부동산 동향 및 분석
- 서비스 소개
- AI 채팅창
- AI Action 실행

        ↓

[Spring Boot]
메인 서버
- 회원/로그인
- 매물 CRUD 및 검색
- 관심매물
- 부동산 DB
- POI DB
- 분석 데이터 API
- 사용자 권한/인증
- 일반 REST API
- 현재 사용자 상태를 AI 서버에 전달
- FastAPI와 통신

        ↓

[FastAPI]
AI 전용 서버
- OpenAI API 호출
- AI Agent 로직
- Prompt
- Tool Calling
- RAG
- App Knowledge
- AI Context 처리
- Tool 선택
- AI 자연어 응답 생성
- 향후 머신러닝/가격예측 모델 추가 가능

        ↓

[외부/내부 자원]
- OpenAI API
- 부동산법 Vector DB
- App Knowledge Vector DB
- 향후 ML 모델
- 필요 시 기타 외부 API


============================================================
3. Spring Boot와 FastAPI의 역할 분리
============================================================

3-1. Spring Boot = 메인 서비스 서버

Spring Boot가 부동산 서비스 자체의 "주인"이 된다.

담당 기능:
- 회원가입 / 로그인
- 사용자 정보
- 매물 데이터
- 매물 검색
- 관심매물
- POI
- 실거래가/분석용 데이터
- DB 접근
- 권한/보안
- Frontend용 일반 API
- FastAPI에 필요한 데이터를 제공하는 내부 API

중요 원칙:
부동산 서비스 DB에 대한 핵심 비즈니스 로직은 Spring Boot에 유지한다.

예)
FastAPI가 직접 DB에 SQL을 날리기보다는,

FastAPI
→ Spring Boot 내부 API
→ Service
→ Repository
→ DB

구조를 우선 고려한다.

이렇게 해야 비즈니스 로직이 Java와 Python 양쪽에 흩어지는 것을 줄일 수 있다.


3-2. FastAPI = AI 전용 서버

FastAPI는 AI 두뇌 역할을 한다.

담당 기능:
- OpenAI API 연결
- AI Agent
- 공인중개사 역할 Prompt
- Tool Calling
- 부동산법 RAG
- App Knowledge RAG
- 사용자 질문 의도 판단
- 여러 Tool을 어떤 순서로 사용할지 판단
- Tool 결과를 종합하여 자연어로 설명
- 향후 pandas / NumPy / scikit-learn / PyTorch 모델 추가


============================================================
4. AI Agent가 이해해야 할 5가지
============================================================

AI가 우리 웹사이트를 제대로 활용하려면 다음 5가지를 연결해야 한다.


4-1. Prompt

AI가 "어떻게 행동해야 하는가"를 정의한다.

예)
- 전문적인 공인중개사처럼 정중하게 말한다.
- 어려운 부동산 용어는 쉽게 설명한다.
- 장점만 말하지 않고 위험요소도 함께 설명한다.
- 매수를 강요하거나 투자수익을 보장하지 않는다.
- 법률 관련 내용은 가능한 한 RAG 근거를 확인한다.
- 확실하지 않은 내용을 단정하지 않는다.

초기에는 Fine-tuning이 아니라 Prompt로 충분하다.


4-2. RAG

AI가 "어떤 문서를 참고해야 하는가"를 담당한다.

A. 부동산법 RAG
예)
- 주택임대차보호법
- 상가건물 임대차보호법
- 공인중개사법
- 민법 관련 조항
- 부동산거래신고 관련 법령
- 기타 필요한 공식 법률 자료

법률은 개정될 수 있기 때문에 Fine-tuning으로 외우게 하기보다
최신 문서를 검색해서 답하는 RAG가 적합하다.

B. App Knowledge RAG
우리 서비스 자체를 설명하기 위한 자료

예)
- 서비스 소개
- 제작 목적
- 제작자/팀 정보
- 페이지별 기능 설명
- 사용방법
- FAQ
- 각 메뉴의 역할

예)
사용자:
"현재 이 앱은 누가 만든 거야?"

AI:
- App Knowledge 검색
- 소개 페이지 이동 Tool 호출
- 소개 페이지로 실제 화면 이동
- 관련 내용을 자연어로 설명


4-3. Tool

AI가 "무엇을 할 수 있는가"를 정의한다.

Tool은 AI가 웹사이트와 백엔드를 사용하기 위한 리모컨이다.

예)

[매물 Tool]
search_properties()
get_property_detail()
compare_properties()

[관심매물 Tool]
get_favorites()
add_favorite()
remove_favorite()

[분석 Tool]
get_market_analysis()
run_market_analysis()

[POI Tool]
search_subway()
search_school()
search_hospital()
search_pharmacy()
search_poi()

[법률 Tool]
search_real_estate_law()

[App Knowledge Tool]
search_app_knowledge()

[지도/UI Tool]
move_map()
zoom_map()
fit_bounds()
highlight_properties()
open_property_detail()
navigate_page()
select_analysis_station()
select_analysis_region()
set_analysis_trade_type()
run_analysis_ui()

중요:
AI에게 arbitrary JavaScript 실행 권한을 주지 않는다.
eval(), 임의 DOM 수정 등은 금지한다.

AI는 미리 허용된 Tool만 호출하게 한다.


4-4. App State / User Context

AI가 "사용자가 지금 무엇을 보고 있는가"를 이해하게 한다.

매 요청마다 필요한 상태를 AI에게 전달한다.

예)

{
  "current_page": "map",
  "map_center": {
    "lat": 37.394,
    "lng": 127.111
  },
  "zoom": 15,
  "selected_region": "성남시 분당구 정자동",
  "selected_property_id": 427,
  "favorite_property_ids": [182, 427, 903],
  "filters": {
    "property_type": "아파트",
    "max_price": 800000000
  }
}

AI에게 HTML 전체나 DOM 전체를 주기보다는
의미 있는 상태를 구조화된 JSON으로 전달하는 것이 좋다.


4-5. App Structure / Manifest

AI가 웹사이트에 어떤 페이지와 기능이 있는지 알게 한다.

예)

- map
  - 지도 기반 매물 검색

- analysis
  - 지역/역 기준 매매가, 전세가, 거래량 분석

- favorites
  - 관심매물 목록 및 비교

- about
  - 서비스 소개 및 제작자 정보

AI에게 실제 URL 자체를 외우게 하기보다,
navigate_page("market_analysis") 같은 추상화된 Tool을 제공하는 것이 좋다.

실제 URL이 변경되어도 Tool 내부 코드만 수정하면 된다.


============================================================
5. AI가 웹페이지를 조작하는 원리
============================================================

AI가 실제 브라우저에서 마음대로 클릭하는 것이 아니다.

흐름:

사용자
→ AI 질문
→ FastAPI
→ LLM이 필요한 Tool 판단
→ Tool 실행 또는 UI Action 생성
→ Spring Boot / Frontend가 실제 기능 실행

예)

사용자:
"판교역 8억 이하 아파트 보여줘."

1. LLM 판단
search_properties 필요

2. FastAPI Tool 실행
search_properties(
  location="판교역",
  max_price=800000000,
  property_type="아파트"
)

3. FastAPI가 Spring Boot 내부 API 호출

4. Spring Boot가 DB 검색

5. FastAPI가 검색 결과를 LLM에게 다시 전달

6. LLM이 다음 행동 결정
- 지도 이동
- 매물 마커 강조

7. FastAPI → Spring → Frontend로 Action 전달

예)

{
  "message": "조건에 맞는 매물 3건을 찾았습니다.",
  "actions": [
    {
      "type": "MOVE_MAP",
      "lat": 37.394,
      "lng": 127.111,
      "zoom": 15
    },
    {
      "type": "HIGHLIGHT_PROPERTIES",
      "property_ids": [101, 253, 811]
    }
  ]
}

8. Frontend가 Action 실행

MOVE_MAP
→ 네이버지도 이동

HIGHLIGHT_PROPERTIES
→ 해당 매물 마커 강조


============================================================
6. 기존 웹페이지와 AI 연결 방법
============================================================

기존에 만들어 놓은 페이지와 기능을 다시 AI용으로 새로 만들 필요는 없다.

기존 기능을 AI가 호출하기 쉬운 인터페이스로 감싸면 된다.

예)

기존 웹페이지 기능:
- 판교역 선택
- 거래유형 매매 선택
- 분석 버튼 클릭
- 그래프 출력

AI용 Action:
navigate_page("analysis")
select_analysis_station("판교역")
set_analysis_trade_type("매매")
run_market_analysis()

AI가 이 Tool/Action을 호출하면
기존 UI 코드가 그대로 실행된다.

중요:
그래프를 AI가 이미지로만 읽게 하기보다는
그래프의 원본 분석 데이터를 AI에도 전달하는 것이 더 좋다.

예)

분석 API
├─ Frontend 그래프에 데이터 제공
└─ AI Agent에도 동일한 데이터 제공

이렇게 하면 AI가 더 정확하게 결과를 설명할 수 있다.


============================================================
7. Fine-tuning은 현재 단계에서는 필요하지 않음
============================================================

현재 목표에서는 다음 방법으로 충분하다.

공인중개사 말투/태도
→ Prompt

법률 지식
→ RAG

웹사이트 설명
→ App Knowledge / RAG

현재 지도 및 사용자 상태
→ Context / App State

매물 검색
→ Tool

지도/UI 조작
→ Tool

관심매물
→ Tool

분석
→ Tool

따라서 초기 버전에서 Fine-tuning은 필요하지 않다.

Fine-tuning은 나중에 실제 상담 로그와 좋은 답변 사례가 충분히 쌓인 뒤,
특정 상담 패턴이나 일관된 답변 스타일이 필요할 때 검토한다.

예)
- 항상 정해진 상담 순서를 지키게 하고 싶을 때
- 우리 서비스만의 상담 스타일을 매우 일관되게 만들고 싶을 때
- Prompt를 계속 개선해도 특정 행동이 반복적으로 잘 안 될 때

법률 지식이나 매물 데이터를 Fine-tuning에 넣는 것은 권장하지 않는다.
법과 매물 정보는 계속 바뀌므로 RAG/DB 조회가 적합하다.


============================================================
8. OpenAI API와 오픈소스 LLM
============================================================

초기에는 OpenAI API 사용을 우선 고려한다.

장점:
- 직접 GPU 서버 운영 불필요
- Tool Calling 성능이 좋음
- 구축이 빠름
- AI Agent 개발 자체에 집중 가능

OpenAI API 사용 시:
GPT 모델은 OpenAI 서버에서 실행된다.

우리 서버는 GPT 모델을 직접 실행하는 것이 아니라
API 요청만 보낸다.

구조:

FastAPI
→ OpenAI API
→ GPT
→ FastAPI


향후 오픈소스 LLM도 교체 가능하도록 LLM Provider를 추상화하는 것이 좋다.

예)

AI Agent
  ↓
LLM Provider
  ├─ OpenAI
  └─ Local / Hosted Open Model

이렇게 하면 나중에 Qwen, gpt-oss 등의 모델로 비교 테스트할 수 있다.

============================================================
10. Render 테스트 배포
============================================================

Render 계정 하나로 여러 서비스를 만들 수 있다.

예)

Render Workspace

- Spring Boot Service
- FastAPI Service

둘을 같은 Region에 두는 것을 권장한다.

구조:

인터넷
→ Spring Boot
→ FastAPI
→ OpenAI API

가능하면 FastAPI는 외부 사용자에게 직접 노출하지 않고
Spring Boot만 접근하도록 구성한다.

테스트 초기에는 FastAPI Web Service로 띄워
Swagger /docs를 사용하며 테스트해도 좋다.

주의:
Render 무료 서비스는 일정 시간 미사용 시 sleep 상태가 될 수 있어
첫 요청이 느려지는 Cold Start가 발생할 수 있다.

이 현상은 Spring + FastAPI 분리 구조 때문이 아니라
무료 인스턴스의 특성 때문이다.


============================================================
11. AWS EC2 운영 방향
============================================================

초기 운영에서는 Spring Boot와 FastAPI를
같은 EC2 한 대에 실행할 수도 있다.

예)

AWS EC2
├─ Nginx
├─ Spring Boot :8080
└─ FastAPI :8000

Spring Boot
→ localhost:8000
→ FastAPI

FastAPI 포트는 외부에 공개하지 않아도 된다.

사용자가 늘어나면 이후에 분리 가능하다.

EC2 #1
Spring Boot

        ↓ AWS 내부망

EC2 #2
FastAPI

즉 처음부터 서버 두 대를 운영할 필요는 없다.


============================================================
12. 성능 관련
============================================================

Spring Boot와 FastAPI 사이에 HTTP 통신이 한 번 추가되지만,
AI 채팅에서 전체 지연의 대부분은 보통 다음에서 발생한다.

- OpenAI API
- LLM 추론
- RAG 검색
- 여러 Tool의 연속 호출

Spring ↔ FastAPI가 같은 머신 또는 같은 리전에 있으면
추가 통신 지연은 비교적 작은 편이다.

따라서 구조 분리 자체가 심각한 성능 저하를 만드는 것은 아니다.

사용자 경험을 위해서는 Streaming 응답을 고려한다.

예)
전체 답변이 완성된 뒤 한 번에 출력
X

토큰 생성과 동시에 채팅창에 조금씩 출력
O

13. 추천 개발 순서
============================================================

[0단계] 현재 웹사이트 정리
- 현재 페이지 목록 정리
- 지도 기능 정리
- 매물 기능 정리
- 분석 페이지 기능 정리
- 관심매물 기능 정리
- AI가 나중에 조작해야 할 기능 목록 작성


[1단계] Spring Boot ↔ FastAPI 연결

목표:
Java 서버와 Python 서버가 통신하는 구조 이해

Spring:
POST /api/ai/test

FastAPI:
POST /agent/test

처음에는
Spring → FastAPI → "hello"
정도만 성공시키면 된다.


[2단계] FastAPI ↔ OpenAI API 연결

목표:
일반 AI 채팅 구현

Frontend
→ Spring
→ FastAPI
→ OpenAI
→ FastAPI
→ Spring
→ Frontend


[3단계] 공인중개사 Prompt 적용

목표:
AI의 기본 말투와 행동 원칙 확립

- 전문적
- 정중한 상담
- 위험도 설명
- 과도한 매수 권유 금지
- 불확실성 표시


[4단계] AI Chat UI와 현재 App State 연결

Frontend가 FastAPI에 전달할 정보:
- 현재 페이지
- 지도 중심
- zoom
- 지도 bounds
- 선택 지역
- 선택 매물
- 관심매물
- 필터


[5단계] 첫 번째 Tool: 매물 검색

FastAPI Agent
→ search_properties Tool
→ Spring Boot 매물 API
→ DB
→ 검색 결과
→ AI

가장 먼저 완성할 핵심 Tool이다.


[6단계] 지도 UI Action

AI가 결과를 Frontend Action으로 반환하도록 한다.

예)
MOVE_MAP
FIT_BOUNDS
HIGHLIGHT_PROPERTIES
OPEN_PROPERTY

이 단계가 완성되면
"AI가 지도와 대화한다"는 느낌이 본격적으로 생긴다.


[7단계] 관심매물 Context 및 Tool

예)

add_favorite()
remove_favorite()
compare_favorites()

사용자:

같은 대화 구현.


[8단계] App Structure / 페이지 이동 Tool

예)
navigate_page("about")

navigate_page("favorites")

사용자:
"현재 이 앱은 누가 만든 거야?"
→ 소개 페이지 이동 + 설명


[9단계] 부동산 분석 페이지 Tool

예)
select_analysis_station()
select_analysis_region()
set_analysis_trade_type()
run_market_analysis()

사용자:
"판교역 매매가 분석을 보여줘."
→ 분석 페이지 이동
→ 판교역 선택
→ 매매 선택
→ 분석 실행
→ 그래프 표시
→ 결과 자연어 해석


[10단계] App Knowledge 구축

서비스 소개
사용방법
페이지별 기능
FAQ

작으면 Prompt/Manifest로 제공하고,
내용이 커지면 App Knowledge RAG로 분리.


[11단계] 부동산법 RAG 구축

공식 법률 문서를 수집하고
Vector DB에 저장.

[12단계] POI 및 실거래/분석 Tool

지도와 분석 기능을 더 풍부하게 만든다.


[13단계] 다단계 Agent 동작

한 질문에 여러 Tool을 순서대로 호출하게 한다.

예)

사용자:
"내가 찜한 판교 매물과 비슷한 가격의 집을 찾아서
최근 3년 가격 흐름도 비교해줘."

AI:
get_favorites()
→ get_property_detail()
→ search_properties()
→ get_market_analysis()
→ compare_properties()
→ highlight_properties()
→ 최종 설명


[14단계] Streaming 및 UX 개선

- 토큰 Streaming
- Tool 실행 중 상태 표시
- "매물을 검색하고 있습니다"
- "지도에 표시했습니다"
- Action 실행 애니메이션
- 에러/재시도 처리


[15단계] 로그와 평가 데이터 축적

저장할 수 있는 것:
- 사용자 질문
- AI 답변
- Tool 호출
- Tool 인자
- Tool 결과
- 사용자 피드백

이 데이터를 바탕으로
Prompt 개선 → Agent 개선 → 필요 시 Fine-tuning 검토.

14. 최종 완성 형태
============================================================

최종적으로는 사용자가 메뉴 구조를 몰라도 된다.

예)

사용자:
"판교에서 출퇴근하기 좋고 8억 이하인 아파트 찾아줘."

AI:
- 판교역 기준 검색
- 지도 이동
- 매물 검색
- 후보 표시
- 설명

사용자:
"두 번째 거 찜해줘."

AI:
- 관심매물 등록

사용자:
"그 집 주변 가격 흐름 보여줘."

AI:
- 분석 페이지 이동
- 해당 지역 자동 선택
- 매매가 그래프 실행
- 자연어 해석

사용자:
"전세로 들어간다면 법적으로 뭘 확인해야 해?"

AI:
- 부동산법 RAG 검색
- 필요한 확인사항 및 위험요소 설명

즉,

"대화가 웹사이트의 통합 인터페이스"

가 되는 것이 최종 목표다.


============================================================
15. 핵심 설계 원칙 요약
============================================================

1. Spring Boot는 메인 서버이자 부동산 서비스 데이터/비즈니스 로직의 주인으로 둔다.

2. FastAPI는 AI Agent 전용 서버로 둔다.

3. GPT는 직접 DB나 웹페이지를 조작하지 않는다.

4. AI에게 허용된 Tool만 제공한다.

5. 지도/UI 변경은 Frontend가 Action을 받아 실제로 실행한다.

6. AI에게 HTML 전체보다 App State를 구조화해서 전달한다.

7. 법률과 자주 바뀌는 데이터는 Fine-tuning하지 않고 RAG/DB를 사용한다.

8. 현재 단계에서는 Fine-tuning이 필요 없다.

9. 처음에는 OpenAI API로 Agent 기능을 완성하는 것이 가장 빠르다.

10. 나중에 오픈소스 LLM을 사용할 수 있도록 LLM 호출 계층은 가능하면 분리한다.

11. Render에서는 하나의 계정에서 Spring Boot와 FastAPI를 각각 별도 서비스로 테스트할 수 있다.

12. AWS에서는 처음에는 같은 EC2에 Spring Boot와 FastAPI를 같이 띄우고,
    트래픽이 커지면 서버를 분리해도 된다.

13. 처음부터 모든 기능을 만들지 말고,
    "AI 채팅 → 매물 검색 Tool → 지도 Action"
    이 3가지를 먼저 완성하는 것이 가장 중요하다.

→ Spring

이후 관심매물, 분석, 페이지 이동, RAG 등은 같은 구조를 확장하면 된다.
